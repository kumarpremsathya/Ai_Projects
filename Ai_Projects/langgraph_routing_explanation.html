LangGraph Routing Flow — Reference Notes

File: langraph_with_multiple_tool.py

0. Where State Is Saved and How It Flows

Important correction: AgentState is not an object/class where values are stored. It is only a schema/type definition. It describes which keys a state dictionary may contain: 

class AgentState(TypedDict):
        query: str
        messages: Annotated[list, add_messages]
        intermediate_steps: list[str]
        tool_output: Optional[str]
        final_answer: Optional[str]
        next_step: str

The actual values live in LangGraph's runtime state dictionary. Because this graph is compiled with a SqliteSaver checkpointer, LangGraph also saves each merged state checkpoint in rag_checkpoints.sqlite, under the current thread_id. 

memory = SqliteSaver(conn)
graph = builder.compile(checkpointer=memory)

Actual state flow

User question
    ↓
ask_question creates initial_state dictionary
    ↓
graph.invoke(initial_state, config)
    ↓
LangGraph gives current state to agent_node(state)
    ↓
agent_node returns an update dictionary
    ↓
LangGraph merges update into current state and checkpoints it
    ↓
route_next(merged_state) chooses a tool node
    ↓
LangGraph gives the same merged state to that tool node
    ↓
tool node returns another update dictionary with ToolMessage/result
    ↓
LangGraph merges it, checkpoints it, follows fixed edge back to agent_node
    ↓
repeat until agent_node causes route_next to return END

Step 1: Initial state is created

Inside ask_question, the user's question is added to messages:

messages.append({"role": "user", "content": question})

initial_state = {"query": question, "messages": messages}
result = graph.invoke(initial_state, config=config)

At this point, it is normal that fields such as tool_output, next_step, and final_answer do not exist yet. Nodes add them later.

Step 2: LangGraph calls agent_node(current_state)

LangGraph passes the complete current state into the node:

def agent_node(state: AgentState):
        messages = state["messages"]
        ...

The LLM returns either tool calls or a final answer. agent_node then creates an update, not a complete replacement state: 

update = {
        "messages": [response],
        "intermediate_steps": intermediate_steps,
        "next_step": next_step,
        "final_answer": final_answer,
}
return update

Step 3: LangGraph merges and saves the update

LangGraph merges the returned update into its current state. Most fields replace their previous values; for example, next_step may change from None to "search_documents".

messages is special because it uses the add_messages reducer:

messages: Annotated[list, add_messages]

Therefore, returning {"messages": [response]} appends the new AIMessage rather than replacing the existing conversation history. 

Before agent_node:
messages = [SystemMessage, HumanMessage]

After agent_node:
messages = [SystemMessage, HumanMessage, AIMessage(tool_calls=[...])]
next_step = "search_documents"

After merging, SqliteSaver saves the state checkpoint for that thread.

Step 4: route_next reads the merged state

Only after state is merged does LangGraph call route_next(state). That router receives the latest state, including state["next_step"], and returns a decision key. The path map then resolves that key to the next node.

Step 5: The selected tool node receives the same current state

For example, LangGraph invokes:

search_documents_node(state)

That wrapper delegates to:

_run_tool_node(state, "search_documents")

The tool node reads the latest AI tool-call request, invokes the real tool, and returns another partial update:

last_message = state["messages"][-1]
output = tools_by_name[tool_name].invoke(tool_call["args"])

update = {
        "messages": tool_messages,
        "tool_output": tool_output,
        "intermediate_steps": intermediate_steps,
        "next_step": "agent_node",
}
return update

LangGraph merges and checkpoints this update. The new ToolMessage is appended to messages, and tool_output becomes the most recent tool result.

Step 6: The fixed edge returns to agent_node

This return happens because the graph declares a fixed edge:

builder.add_edge("search_documents_node", "agent_node")

It does not happen because the tool node stored next_step = "agent_node". That value is saved and passed forward, but this fixed edge does not read it. The next agent_node call receives the updated state, including the ToolMessage, and the LLM decides whether another tool is needed or whether it can provide the final answer.

Best mental model:
  • AgentState: blueprint of possible state keys, not storage.
  • LangGraph runtime state: the actual dictionary containing values.
  • Node function: receives current state and returns a partial update.
  • LangGraph: merges updates, persists them through SqliteSaver, and moves execution along edges.
  • messages: accumulates because of add_messages.
  • next_step: only affects routing when route_next reads it after agent_node.

0.1 How the LLM Chooses a Tool

Important refinement: agent_node does not decide which tool to call by itself. Inside agent_node, this call asks the LLM to decide: 

response = llm_with_tools.invoke(messages)

The LLM can return either:

  1. a normal final answer, or
  2. structured tool_calls, for example:
{
    "name": "search_documents",
    "args": {"input": "Cloud Engineering manager"}
}

Your Python code then reads the LLM's response:

if response.tool_calls:
    next_step = response.tool_calls[0]["name"]
else:
    next_step = "end"

Decision chain

User question + system prompt + earlier messages/tool results
        ↓
agent_node sends all messages to LLM
        ↓
LLM decides: final answer OR tool call(s)
        ↓
agent_node converts first requested tool into next_step
        ↓
route_next sends graph to that matching tool node

How the LLM knows which tool to call

This line gives the LLM the available tool definitions:

llm_with_tools = groq_llm.bind_tools(tools)

And tools contains:

tools = [search_documents, search_database, web_search]

Each @tool function provides the LLM with a tool name, input schema, and docstring. The LLM uses those descriptions together with the system prompt and the user's question to choose a tool.

search_documents

The tool description directs the LLM to use it for AcmeNova company information, employees, policies, head office, and the Coolie movie.

Example user question:

Who manages Cloud Engineering?

The LLM sees “Cloud Engineering” as an AcmeNova employee/company fact, so it can return: 

search_documents(input="Cloud Engineering manager")

search_database

The tool description directs the LLM to use it for users, accounts, emails, account status, user counts, and signup data.

Example user question:

How many inactive users are there?

Expected LLM tool call:

search_database(input="How many inactive users are there?")

web_search

The tool description directs the LLM to use it for current information, recent news, or information not in the documents/database.

Example user question:

Who won IPL 2026?

Expected LLM tool call:

web_search(input="IPL winner 2026")

Your system prompt also guides the LLM

In ask_question, the system message adds stricter rules:

Use search_documents ONLY for AcmeNova company facts.
Use search_database for users, accounts, emails, or signup data.
Use web_search for real-world names/current information.

So the LLM makes its tool choice using three inputs:

1. User question
2. Tool names + docstrings
3. Your system prompt rules

What happens after a tool response

After a tool node returns a ToolMessage, the fixed edge sends execution back to agent_node. The LLM sees the full history again: 

User question
→ AIMessage requesting tool
→ ToolMessage containing tool result

Then it decides again:

Do I have enough information?
    Yes → return final answer
    No  → request another tool

For example:

Question: “IPL winner 2026 and AcmeNova head office?”

agent_node call 1:
  LLM requests web_search("IPL winner 2026")

web_search_node:
  returns ToolMessage with IPL result

agent_node call 2:
  LLM sees IPL result but still needs office location
  LLM requests search_documents("AcmeNova head office")

search_documents_node:
  returns ToolMessage with office result

agent_node call 3:
  LLM sees both results
  LLM produces final answer
Current limitation: if the LLM requests multiple different tools in one response, this script takes only response.tool_calls[0]["name"]. The graph therefore executes only the first requested tool in that pass.

0.2 What Counts as a Tool-Use Loop

The clean terminology is:

  • One graph run: one graph.invoke(...) call for one user message.
  • One tool-use loop / cycle: agent_node → one tool node → agent_node.
  • Final exit: the last agent_node runs, produces an answer instead of a tool call, then routes to END.

For a user question that needs two tools sequentially:

User question
    ↓
agent_node
    ↓ LLM asks web_search
web_search_node
    ↓ fixed edge
agent_node
    ↓ LLM asks search_documents
search_documents_node
    ↓ fixed edge
agent_node
    ↓ LLM has enough information and answers
END

That graph run contains:

  1. Tool-use loop 1: agent_node → web_search_node → agent_node
  2. Tool-use loop 2: agent_node → search_documents_node → agent_node
  3. Final agent pass: agent_node → END
It is not automatically “first user sub-question = first loop, second user sub-question = second loop.” The LLM decomposes a compound request internally and decides what information it still needs after each ToolMessage. It can also call the same tool twice if the first result is insufficient: 
agent_node → search_documents_node → agent_node
agent_node → search_documents_node → agent_node
agent_node → END

For a completely new user question, ask_question(...) calls graph.invoke(...) again, starting a new graph run. If the thread_id is the same, that new run begins with prior messages/checkpoints in state; if it has a new thread_id, it begins with fresh conversation state.

0.3 What Happens When a Tool Does Not Find an Answer

The LLM can call another tool after an unsuccessful tool result, but the current graph does not guarantee or enforce that fallback behavior.

For example, suppose the user asks for AcmeNova's head-office address, but the LLM incorrectly chooses:

search_database(...)

The graph flow is still:

agent_node
    → search_database_node
    → ToolMessage containing database result / “no result”
    → fixed edge back to agent_node

When agent_node runs again, the LLM receives that database ToolMessage in state["messages"]. It can decide to:

  1. Call search_documents instead.
  2. Retry search_database with a better query.
  3. Call web_search.
  4. Produce a final answer.

Therefore, another tool can be called in the next loop:

agent_node
    → search_database_node
    → agent_node
    → search_documents_node
    → agent_node
    → END

Is fallback handled explicitly in this script? No. There is no deterministic rule such as: If database result is empty, automatically call search_documents. The fallback depends on the LLM noticing that the result is missing or insufficient and choosing another tool during its next agent_node call.

Your system prompt helps guide this behavior:

Use search_documents ONLY for AcmeNova company facts.
Use search_database for questions about users, accounts, emails, or signup data.

But this is an instruction to the LLM, not enforced routing logic. The prompt also says: 

Do not call both tools for the same sub-question if one tool already returned a clear answer.

The key phrase is "clear answer." If search_database returns no answer, the LLM is allowed to try another relevant tool. But it may not do so reliably; it could retry the wrong tool or answer without enough evidence.

Summary

Tool returns useful answer
  → LLM normally produces final answer

Tool returns missing/unclear answer
  → LLM may call another tool
  → but only if the LLM decides to do it

Tool returns error/empty result
  → there is no explicit fallback rule in current code
Reliability implication: for reliable fallback, add application-controlled logic after a tool runs. It can detect "No relevant documents were found.", an empty SQL result, or "SQL execution failed", then route to a defined fallback node.

What the current code actually does: _run_tool_node stores the raw result in tool_output, but it does not classify that result as successful, empty, or failed. Each tool node has a fixed add_edge(tool_node, "agent_node"), so it always returns to the LLM. For SQL, an empty query result currently appears inside text such as Query: SELECT ... Result: []; it is not a separate state flag that routing can inspect.

Deterministic fallback solution

This solution is not implemented in the current script. Add a result-status field such as tool_status to AgentState, have each tool node set it to "success", "empty", or "error", then attach a conditional edge to the tool node (or to a separate result-check node). That router can select a defined fallback instead of relying on the next LLM decision. 

search_database_node
    ↓ returns tool_status = "empty"
result_router
    ↓ deterministic rule
search_documents_node  (only when this is an approved fallback)
    ↓
agent_node

The fallback should be domain-specific: for an AcmeNova company fact, an empty database result could route to search_documents_node; for a user/account question, it should usually return a clear "no matching record" result instead of searching company documents.

Core distinction (keep this in mind while reading everything below):
  • LangGraph decides which node(s) get executed — it owns node execution and routing: calling node functions, evaluating conditional edges (via your route_next), following fixed edges, and deciding what runs next.
  • State is just data that gets passed to each node — it is not a control mechanism by itself. state (including fields like next_step) only influences routing when your own code (e.g. route_next) chooses to read a field and returns a decision based on it. LangGraph never inspects state contents on its own; it only inspects the return value of the router function you registered.

1. Corrected Routing Flow

  1. agent_node runs, the LLM requests a tool (e.g. search_documents), and the node returns {"next_step": "search_documents", ...} → state is merged, so state["next_step"] == "search_documents".
  2. LangGraph sees agent_node has a conditional edge attached, so instead of following a fixed add_edge, it calls route_next(state).
  3. Inside route_next, choice = state["next_step"] reads "search_documents" → matches the if choice == "search_documents": branch → function returns the decision key "route_docs" (an abstract label, not a node name).
  4. LangGraph takes that returned string "route_docs" and looks it up as a key in the path map dict passed to add_conditional_edges: 
    {
    "route_docs": "search_documents_node",
    "route_db": "search_database_node",
    "route_web": "web_search_node",
    END: END,
}
  5. The dict's value for that key — "search_documents_node" — tells LangGraph which registered node (added via builder.add_node("search_documents_node", search_documents_node)) to actually execute next.
Key takeaway: the router's return value and the executed node are two separate things, joined only by the path map dict. route_next only classifies what decision was made; the dict decides where execution goes.

2. Why Tools Can't Be Registered as Nodes Directly

builder.add_node(name, fn) requires fn to have the signature fn(state: AgentState) -> dict. A LangChain tool (created via @tool) has a completely different interface: tool.invoke(args_dict) -> output. It doesn't know about your AgentState, doesn't read state["messages"], and doesn't return a state-update dict with messages / tool_output / next_step keys.

That's exactly why _run_tool_node exists — it's the adapter between the two interfaces: 

def _run_tool_node(state: AgentState, tool_name: str):
    last_message = state["messages"][-1]                     # 1. read state
    matching_calls = [tc for tc in last_message.tool_calls if tc["name"] == tool_name]
    ...
    output = tools_by_name[tool_name].invoke(tool_call["args"])   # 2. call the actual tool
    tool_messages.append(ToolMessage(content=str(output), ...))  # 3. wrap result back into a message
    return {"messages": tool_messages, "tool_output": ..., "next_step": "agent_node"}  # 4. state update
StepWhat happens
1. Read statePull the last AIMessage and find the tool_calls matching this node's tool name.
2. Call the toolInvoke the actual LangChain tool with the call's raw arguments.
3. Wrap resultPackage the tool's raw output into a ToolMessage, tagged with the matching tool_call_id.
4. State updateReturn a partial state patch (messages, tool_output, next_step) for LangGraph to merge.
Bottom line: the node isn't "the tool" — it's glue code that bridges the state-machine world (LangGraph) and the tool-invocation world (LangChain tools). Tools have no concept of AgentState, ToolMessage, or next_step; only your node functions do.

3. Node Name vs. Function Reference

In builder.add_node("search_documents_node", search_documents_node):

  • "search_documents_node" (the string, first argument) — this is the node name. It's just a label/identifier LangGraph uses internally to refer to this step in the graph (used in add_edge, the route_next path map, visualizations, etc.).
  • search_documents_node (no quotes, second argument) — this is the function reference (defined earlier in the file): 
    def search_documents_node(state: AgentState):
    return _run_tool_node(state, "search_documents")
    This is the actual Python callable LangGraph invokes (passing it state) whenever execution reaches that node.
They happen to share the same text here, which is a common convention but not required — you could write builder.add_node("docs_step", search_documents_node) and reference "docs_step" in edges/path map instead. The string is purely an internal graph label; the unquoted name is Python resolving the actual function object to call.

5. How the Multi-Tool Loop Actually Works (IMPORTANT)

A conditional edge is attached to the node, not to a single execution. Every single time agent_node finishes running — no matter how many times it's re-entered in a loop — LangGraph re-evaluates route_next(state) fresh, using whatever state["next_step"] is at that moment. The same conditional-edge configuration is reused every cycle; it is never "used up" after firing once.

The graph shape (a cycle, not a straight line)

                 ┌──────────────────────────────────────────┐
                 │                                            │
 START ──▶ agent_node ──(conditional: route_next)──▶ search_documents_node ──▶ (back to agent_node)
                 │                                            
                 ├──(conditional: route_next)──▶ search_database_node ──▶ (back to agent_node)
                 │
                 ├──(conditional: route_next)──▶ web_search_node ──▶ (back to agent_node)
                 │
                 └──(conditional: route_next)──▶ END

add_conditional_edges("agent_node", route_next, {...}) is registered once in the code, but it's a permanent property of the agent_node node — LangGraph calls route_next every time agent_node completes, regardless of which iteration/loop count it is.

Trace: web_search first, then search_documents

Iteration 1

  1. agent_node runs → LLM decides it needs web_search first → next_step = "web_search".
  2. LangGraph calls route_next(state) → choice == "web_search" → returns "route_web".
  3. Path map: "route_web" → "web_search_node".
  4. web_search_node (i.e. _run_tool_node(state, "web_search")) runs, appends a ToolMessage, sets next_step = "agent_node".
  5. Fixed edge add_edge("web_search_node", "agent_node") (no branching, no route_next call here) sends control back to agent_node.

Iteration 2

  1. agent_node runs again (2nd time) → sees the new ToolMessage in context → LLM now decides it needs search_documents → next_step = "search_documents".
  2. LangGraph calls route_next(state) again (fresh call, same function, new state) → choice == "search_documents" → returns "route_docs".
  3. Path map: "route_docs" → "search_documents_node".
  4. search_documents_node runs, appends its own ToolMessage, sets next_step = "agent_node".
  5. Fixed edge add_edge("search_documents_node", "agent_node") sends control back to agent_node.

Iteration 3

  1. agent_node runs a 3rd time → LLM now has both tool results → generates final answer → next_step = "end".
  2. route_next(state) → choice doesn't match "search_documents"/"search_database"/"web_search" → falls through to return END.
  3. Path map: END → END. Graph stops.

The two edge types working together

  • add_conditional_edges("agent_node", route_next, {...}) — this is the only branching point in the whole graph. It fires every single time agent_node finishes, and picks 1 of 4 destinations based on the current next_step value in state.
  • add_edge(tool_node, "agent_node") (×3, one per tool) — these are dumb, fixed edges. No decision, no function call — every tool node always funnels back to agent_node.
Bottom line: the "looping" across 2+ different tools isn't special-cased anywhere in the code — it emerges naturally because agent_node is a cycle re-entry point, and each time you land back on it, the same conditional edge re-evaluates against whatever the LLM decided this time. The loop only terminates when route_next returns END, which only happens when agent_node sets next_step = "end" (i.e., the LLM stopped requesting tools).

6. LangGraph Engine vs. Your Application Code

Mixing up "what LangGraph's engine does automatically" vs "what your own Python code decides" is exactly what causes confusion about the loop. Here's the clean split.

What LangGraph (the engine) controls

This is generic machinery — it doesn't know or care about tools, LLMs, or your business logic. It just executes whatever graph structure you built with builder.add_node(...) / add_edge(...) / add_conditional_edges(...).

LangGraph's jobWhere it happens
Calling a node function with the current state e.g. it calls agent_node(state), web_search_node(state)
Merging whatever dict a node returns into the shared state (using each field's reducer) happens after every node call, automatically
Persisting the merged state via the checkpointer memory = SqliteSaver(conn)
Deciding which edge type to follow once a node finishes: fixed (add_edge) or conditional (add_conditional_edges) pure graph structure, decided at builder.add_conditional_edges("agent_node", ...) / builder.add_edge("web_search_node", "agent_node")
If conditional: calling your router function (route_next) and using its returned string to look up the path map dict 
builder.add_conditional_edges(
    "agent_node",
    route_next,
    {
        "route_docs": "search_documents_node",
        "route_db": "search_database_node",
        "route_web": "web_search_node",
        END: END,
    },
)
If fixed: just going straight to the hardcoded target node, no function call, no state inspection 
builder.add_edge("search_documents_node", "agent_node")
builder.add_edge("search_database_node", "agent_node")
builder.add_edge("web_search_node", "agent_node")
Key point: LangGraph itself never looks inside state["next_step"]. It has no idea that field exists or what string is in it. The only reason next_step matters at all is because your own route_next function happens to read it — that's your code's decision, not LangGraph's built-in behavior.

What your code (application logic) controls

This is everything LangGraph blindly delegates to your functions.

Your code's jobWhere it happens
Deciding what next_step should be set to agent_node sets it to a tool name or "end"; _run_tool_node always sets it to "agent_node" — but this value is just inert data, not a signal LangGraph acts on
Interpreting next_step to pick a destination 
def route_next(state: AgentState):
    choice = state["next_step"]
    if choice == "search_documents":
        return "route_docs"
    ...
— this is a plain Python function you wrote; LangGraph only calls it because you registered it via add_conditional_edges
Translating the router's decision key into a real node name the path map dict you passed alongside route_next: 
{"route_docs": "search_documents_node", ...}
Deciding which tool to call, based on the LLM's output agent_node's if response.tool_calls: block
Actually invoking the tool and wrapping the result _run_tool_node

Applying this to web_search_node → agent_node

  • _run_tool_node sets next_step = "agent_node" — this is just your code writing a string into a dict field. It has zero effect on LangGraph's routing.
  • LangGraph, after running web_search_node, checks its compiled graph structure: does "web_search_node" have a conditional edge? No — only "agent_node" does, via builder.add_conditional_edges("agent_node", route_next, {...}). So it falls through to the plain edge builder.add_edge("web_search_node", "agent_node") — this is LangGraph's built-in mechanism, following a static graph structure decision made at build time, completely independent of anything in state.
Correcting the common misconception: setting next_step = "agent_node" is coincidental/cosmetic here — it is not what causes the transition. The transition happens purely because of the graph's static edge structure (LangGraph engine), not because LangGraph read that state value (which would be application logic, and in this case, isn't even wired up for tool nodes since they have no conditional edge / router function attached at all).

7. One Conditional Decision Per agent_node Pass

Per iteration/turn, agent_node's conditional edge fires exactly once and picks exactly one destination out of the 4 options (3 tool nodes or END). It's a single decision per pass, based purely on whatever route_next reads from state["next_step"] at that moment.

To be precise about the mechanism:

  1. agent_node runs → its own code sets next_step in the returned dict (based on the LLM's decision — first tool call name, or "end").
  2. State merges → state["next_step"] now holds that value.
  3. LangGraph calls route_next(state) once → reads state["next_step"] → returns one decision key ("route_docs" / "route_db" / "route_web" / END).
  4. The path map dict resolves that single key to one node → only that one node executes this cycle.
So yes — one agent_node execution → one conditional evaluation → one tool node (or END) executed. This is also exactly why the original bug exists: if the LLM's single response contains multiple tool_calls (e.g. search_documents + web_search in the same turn), next_step only captures response.tool_calls[0]["name"] — so even though the LLM asked for 2+ tools in one shot, the conditional edge can still only route to one node per agent_node pass, leaving the rest to be caught (or missed) on a later loop back through agent_node.

8. What Is a Fully Autonomous Agent?

A fully autonomous agent can pursue a goal with broad independence. It can plan multiple steps, choose actions and tools dynamically, check results, adapt when an action fails, and continue until the goal is complete, subject to permissions, budgets, and safety limits.

For example, given "Plan my trip to Delhi under $800," an autonomous agent could:

  1. Search flights and hotels.
  2. Compare the available options against the budget.
  3. Revise the plan when prices change or a search fails.
  4. Ask only the necessary follow-up questions.
  5. Make bookings only when it has the required permission.

This application is not fully autonomous. It is a bounded multi-tool agent: it can use only the three tools you provide, it can follow only the LangGraph paths you define, and it has no explicit, deterministic recovery plan for empty or failed tool results. It also cannot create new tools, grant itself permissions, or take actions outside this graph.

Better wording for this app: the LLM reasons over the conversation and tool results, decides which available tool to call, and the LangGraph workflow executes that action. This bounded design is usually easier to test, secure, and explain than a fully autonomous agent.
