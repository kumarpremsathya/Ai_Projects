LangGraph Routing Flow — Reference Notes

File: langraph_with_multiple_tool.py

1. Corrected Routing Flow

  1. agent_node runs, the LLM requests a tool (e.g. search_documents), and the node returns {"next_step": "search_documents", ...} → state is merged, so state["next_step"] == "search_documents".
  2. LangGraph sees agent_node has a conditional edge attached, so instead of following a fixed add_edge, it calls route_next(state).
  3. Inside route_next, choice = state["next_step"] reads "search_documents" → matches the if choice == "search_documents": branch → function returns the decision key "route_docs" (an abstract label, not a node name).
  4. LangGraph takes that returned string "route_docs" and looks it up as a key in the path map dict passed to add_conditional_edges: 
    {
    "route_docs": "search_documents_node",
    "route_db": "search_database_node",
    "route_web": "web_search_node",
    END: END,
}
  5. The dict's value for that key — "search_documents_node" — tells LangGraph which registered node (added via builder.add_node("search_documents_node", search_documents_node)) to actually execute next.
Key takeaway: the router's return value and the executed node are two separate things, joined only by the path map dict. route_next only classifies what decision was made; the dict decides where execution goes.

2. Why Tools Can't Be Registered as Nodes Directly

builder.add_node(name, fn) requires fn to have the signature fn(state: AgentState) -> dict. A LangChain tool (created via @tool) has a completely different interface: tool.invoke(args_dict) -> output. It doesn't know about your AgentState, doesn't read state["messages"], and doesn't return a state-update dict with messages / tool_output / next_step keys.

That's exactly why _run_tool_node exists — it's the adapter between the two interfaces: 

def _run_tool_node(state: AgentState, tool_name: str):
    last_message = state["messages"][-1]                     # 1. read state
    matching_calls = [tc for tc in last_message.tool_calls if tc["name"] == tool_name]
    ...
    output = tools_by_name[tool_name].invoke(tool_call["args"])   # 2. call the actual tool
    tool_messages.append(ToolMessage(content=str(output), ...))  # 3. wrap result back into a message
    return {"messages": tool_messages, "tool_output": ..., "next_step": "agent_node"}  # 4. state update
StepWhat happens
1. Read statePull the last AIMessage and find the tool_calls matching this node's tool name.
2. Call the toolInvoke the actual LangChain tool with the call's raw arguments.
3. Wrap resultPackage the tool's raw output into a ToolMessage, tagged with the matching tool_call_id.
4. State updateReturn a partial state patch (messages, tool_output, next_step) for LangGraph to merge.
Bottom line: the node isn't "the tool" — it's glue code that bridges the state-machine world (LangGraph) and the tool-invocation world (LangChain tools). Tools have no concept of AgentState, ToolMessage, or next_step; only your node functions do.

3. Node Name vs. Function Reference

In builder.add_node("search_documents_node", search_documents_node):

  • "search_documents_node" (the string, first argument) — this is the node name. It's just a label/identifier LangGraph uses internally to refer to this step in the graph (used in add_edge, the route_next path map, visualizations, etc.).
  • search_documents_node (no quotes, second argument) — this is the function reference (defined earlier in the file): 
    def search_documents_node(state: AgentState):
    return _run_tool_node(state, "search_documents")
    This is the actual Python callable LangGraph invokes (passing it state) whenever execution reaches that node.
They happen to share the same text here, which is a common convention but not required — you could write builder.add_node("docs_step", search_documents_node) and reference "docs_step" in edges/path map instead. The string is purely an internal graph label; the unquoted name is Python resolving the actual function object to call.
