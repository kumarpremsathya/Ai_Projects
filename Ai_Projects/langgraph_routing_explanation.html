LangGraph Routing Flow — Reference Notes

File: langraph_with_multiple_tool.py

Core distinction (keep this in mind while reading everything below):
  • LangGraph decides which node(s) get executed — it owns node execution and routing: calling node functions, evaluating conditional edges (via your route_next), following fixed edges, and deciding what runs next.
  • State is just data that gets passed to each node — it is not a control mechanism by itself. state (including fields like next_step) only influences routing when your own code (e.g. route_next) chooses to read a field and returns a decision based on it. LangGraph never inspects state contents on its own; it only inspects the return value of the router function you registered.

1. Corrected Routing Flow

  1. agent_node runs, the LLM requests a tool (e.g. search_documents), and the node returns {"next_step": "search_documents", ...} → state is merged, so state["next_step"] == "search_documents".
  2. LangGraph sees agent_node has a conditional edge attached, so instead of following a fixed add_edge, it calls route_next(state).
  3. Inside route_next, choice = state["next_step"] reads "search_documents" → matches the if choice == "search_documents": branch → function returns the decision key "route_docs" (an abstract label, not a node name).
  4. LangGraph takes that returned string "route_docs" and looks it up as a key in the path map dict passed to add_conditional_edges: 
    {
    "route_docs": "search_documents_node",
    "route_db": "search_database_node",
    "route_web": "web_search_node",
    END: END,
}
  5. The dict's value for that key — "search_documents_node" — tells LangGraph which registered node (added via builder.add_node("search_documents_node", search_documents_node)) to actually execute next.
Key takeaway: the router's return value and the executed node are two separate things, joined only by the path map dict. route_next only classifies what decision was made; the dict decides where execution goes.

2. Why Tools Can't Be Registered as Nodes Directly

builder.add_node(name, fn) requires fn to have the signature fn(state: AgentState) -> dict. A LangChain tool (created via @tool) has a completely different interface: tool.invoke(args_dict) -> output. It doesn't know about your AgentState, doesn't read state["messages"], and doesn't return a state-update dict with messages / tool_output / next_step keys.

That's exactly why _run_tool_node exists — it's the adapter between the two interfaces: 

def _run_tool_node(state: AgentState, tool_name: str):
    last_message = state["messages"][-1]                     # 1. read state
    matching_calls = [tc for tc in last_message.tool_calls if tc["name"] == tool_name]
    ...
    output = tools_by_name[tool_name].invoke(tool_call["args"])   # 2. call the actual tool
    tool_messages.append(ToolMessage(content=str(output), ...))  # 3. wrap result back into a message
    return {"messages": tool_messages, "tool_output": ..., "next_step": "agent_node"}  # 4. state update
StepWhat happens
1. Read statePull the last AIMessage and find the tool_calls matching this node's tool name.
2. Call the toolInvoke the actual LangChain tool with the call's raw arguments.
3. Wrap resultPackage the tool's raw output into a ToolMessage, tagged with the matching tool_call_id.
4. State updateReturn a partial state patch (messages, tool_output, next_step) for LangGraph to merge.
Bottom line: the node isn't "the tool" — it's glue code that bridges the state-machine world (LangGraph) and the tool-invocation world (LangChain tools). Tools have no concept of AgentState, ToolMessage, or next_step; only your node functions do.

3. Node Name vs. Function Reference

In builder.add_node("search_documents_node", search_documents_node):

  • "search_documents_node" (the string, first argument) — this is the node name. It's just a label/identifier LangGraph uses internally to refer to this step in the graph (used in add_edge, the route_next path map, visualizations, etc.).
  • search_documents_node (no quotes, second argument) — this is the function reference (defined earlier in the file): 
    def search_documents_node(state: AgentState):
    return _run_tool_node(state, "search_documents")
    This is the actual Python callable LangGraph invokes (passing it state) whenever execution reaches that node.
They happen to share the same text here, which is a common convention but not required — you could write builder.add_node("docs_step", search_documents_node) and reference "docs_step" in edges/path map instead. The string is purely an internal graph label; the unquoted name is Python resolving the actual function object to call.

5. How the Multi-Tool Loop Actually Works (IMPORTANT)

A conditional edge is attached to the node, not to a single execution. Every single time agent_node finishes running — no matter how many times it's re-entered in a loop — LangGraph re-evaluates route_next(state) fresh, using whatever state["next_step"] is at that moment. The same conditional-edge configuration is reused every cycle; it is never "used up" after firing once.

The graph shape (a cycle, not a straight line)

                 ┌──────────────────────────────────────────┐
                 │                                            │
 START ──▶ agent_node ──(conditional: route_next)──▶ search_documents_node ──▶ (back to agent_node)
                 │                                            
                 ├──(conditional: route_next)──▶ search_database_node ──▶ (back to agent_node)
                 │
                 ├──(conditional: route_next)──▶ web_search_node ──▶ (back to agent_node)
                 │
                 └──(conditional: route_next)──▶ END

add_conditional_edges("agent_node", route_next, {...}) is registered once in the code, but it's a permanent property of the agent_node node — LangGraph calls route_next every time agent_node completes, regardless of which iteration/loop count it is.

Trace: web_search first, then search_documents

Iteration 1

  1. agent_node runs → LLM decides it needs web_search first → next_step = "web_search".
  2. LangGraph calls route_next(state) → choice == "web_search" → returns "route_web".
  3. Path map: "route_web" → "web_search_node".
  4. web_search_node (i.e. _run_tool_node(state, "web_search")) runs, appends a ToolMessage, sets next_step = "agent_node".
  5. Fixed edge add_edge("web_search_node", "agent_node") (no branching, no route_next call here) sends control back to agent_node.

Iteration 2

  1. agent_node runs again (2nd time) → sees the new ToolMessage in context → LLM now decides it needs search_documents → next_step = "search_documents".
  2. LangGraph calls route_next(state) again (fresh call, same function, new state) → choice == "search_documents" → returns "route_docs".
  3. Path map: "route_docs" → "search_documents_node".
  4. search_documents_node runs, appends its own ToolMessage, sets next_step = "agent_node".
  5. Fixed edge add_edge("search_documents_node", "agent_node") sends control back to agent_node.

Iteration 3

  1. agent_node runs a 3rd time → LLM now has both tool results → generates final answer → next_step = "end".
  2. route_next(state) → choice doesn't match "search_documents"/"search_database"/"web_search" → falls through to return END.
  3. Path map: END → END. Graph stops.

The two edge types working together

  • add_conditional_edges("agent_node", route_next, {...}) — this is the only branching point in the whole graph. It fires every single time agent_node finishes, and picks 1 of 4 destinations based on the current next_step value in state.
  • add_edge(tool_node, "agent_node") (×3, one per tool) — these are dumb, fixed edges. No decision, no function call — every tool node always funnels back to agent_node.
Bottom line: the "looping" across 2+ different tools isn't special-cased anywhere in the code — it emerges naturally because agent_node is a cycle re-entry point, and each time you land back on it, the same conditional edge re-evaluates against whatever the LLM decided this time. The loop only terminates when route_next returns END, which only happens when agent_node sets next_step = "end" (i.e., the LLM stopped requesting tools).

6. LangGraph Engine vs. Your Application Code

Mixing up "what LangGraph's engine does automatically" vs "what your own Python code decides" is exactly what causes confusion about the loop. Here's the clean split.

What LangGraph (the engine) controls

This is generic machinery — it doesn't know or care about tools, LLMs, or your business logic. It just executes whatever graph structure you built with builder.add_node(...) / add_edge(...) / add_conditional_edges(...).

LangGraph's jobWhere it happens
Calling a node function with the current state e.g. it calls agent_node(state), web_search_node(state)
Merging whatever dict a node returns into the shared state (using each field's reducer) happens after every node call, automatically
Persisting the merged state via the checkpointer memory = SqliteSaver(conn)
Deciding which edge type to follow once a node finishes: fixed (add_edge) or conditional (add_conditional_edges) pure graph structure, decided at builder.add_conditional_edges("agent_node", ...) / builder.add_edge("web_search_node", "agent_node")
If conditional: calling your router function (route_next) and using its returned string to look up the path map dict 
builder.add_conditional_edges(
    "agent_node",
    route_next,
    {
        "route_docs": "search_documents_node",
        "route_db": "search_database_node",
        "route_web": "web_search_node",
        END: END,
    },
)
If fixed: just going straight to the hardcoded target node, no function call, no state inspection 
builder.add_edge("search_documents_node", "agent_node")
builder.add_edge("search_database_node", "agent_node")
builder.add_edge("web_search_node", "agent_node")
Key point: LangGraph itself never looks inside state["next_step"]. It has no idea that field exists or what string is in it. The only reason next_step matters at all is because your own route_next function happens to read it — that's your code's decision, not LangGraph's built-in behavior.

What your code (application logic) controls

This is everything LangGraph blindly delegates to your functions.

Your code's jobWhere it happens
Deciding what next_step should be set to agent_node sets it to a tool name or "end"; _run_tool_node always sets it to "agent_node" — but this value is just inert data, not a signal LangGraph acts on
Interpreting next_step to pick a destination 
def route_next(state: AgentState):
    choice = state["next_step"]
    if choice == "search_documents":
        return "route_docs"
    ...
— this is a plain Python function you wrote; LangGraph only calls it because you registered it via add_conditional_edges
Translating the router's decision key into a real node name the path map dict you passed alongside route_next: 
{"route_docs": "search_documents_node", ...}
Deciding which tool to call, based on the LLM's output agent_node's if response.tool_calls: block
Actually invoking the tool and wrapping the result _run_tool_node

Applying this to web_search_node → agent_node

  • _run_tool_node sets next_step = "agent_node" — this is just your code writing a string into a dict field. It has zero effect on LangGraph's routing.
  • LangGraph, after running web_search_node, checks its compiled graph structure: does "web_search_node" have a conditional edge? No — only "agent_node" does, via builder.add_conditional_edges("agent_node", route_next, {...}). So it falls through to the plain edge builder.add_edge("web_search_node", "agent_node") — this is LangGraph's built-in mechanism, following a static graph structure decision made at build time, completely independent of anything in state.
Correcting the common misconception: setting next_step = "agent_node" is coincidental/cosmetic here — it is not what causes the transition. The transition happens purely because of the graph's static edge structure (LangGraph engine), not because LangGraph read that state value (which would be application logic, and in this case, isn't even wired up for tool nodes since they have no conditional edge / router function attached at all).

7. One Conditional Decision Per agent_node Pass

Per iteration/turn, agent_node's conditional edge fires exactly once and picks exactly one destination out of the 4 options (3 tool nodes or END). It's a single decision per pass, based purely on whatever route_next reads from state["next_step"] at that moment.

To be precise about the mechanism:

  1. agent_node runs → its own code sets next_step in the returned dict (based on the LLM's decision — first tool call name, or "end").
  2. State merges → state["next_step"] now holds that value.
  3. LangGraph calls route_next(state) once → reads state["next_step"] → returns one decision key ("route_docs" / "route_db" / "route_web" / END).
  4. The path map dict resolves that single key to one node → only that one node executes this cycle.
So yes — one agent_node execution → one conditional evaluation → one tool node (or END) executed. This is also exactly why the original bug exists: if the LLM's single response contains multiple tool_calls (e.g. search_documents + web_search in the same turn), next_step only captures response.tool_calls[0]["name"] — so even though the LLM asked for 2+ tools in one shot, the conditional edge can still only route to one node per agent_node pass, leaving the rest to be caught (or missed) on a later loop back through agent_node.
